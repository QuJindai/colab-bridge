# Research recipes

`research-pipeline.json` is one serial job: download a pinned small public model, stage training JSONL, benchmark, train a finite LoRA adapter, benchmark the merged adapter, and export a checked ONNX graph. Every path is relative to this job's workspace. It does not depend on another job's inaccessible local directory. The ONNX graph has the fixed tokenized shape of `sample_text`, returns logits, and has no KV cache.

Use the Agent Python with the optional `models` and `onnx` extras. Keep Colab's supplied CUDA-enabled Torch; this package does not pin or replace it with a CPU build. `modelscope` and `drive` are separate optional extras. Model code stays local (`trust_remote_code=False`); download any required model files before benchmark/train/export.

`drive-export-pipeline.json` requires `COLAB_BRIDGE_DRIVE_MOUNT` to name an existing mounted directory in the Agent runtime. Mount export does not create a pretend mount or overwrite an existing destination. API export instead uses `mode: "api"`, `source_path`, optional `name` and `parent_id`, and authorized Application Default Credentials. No tokens or credentials belong in a job spec. The Python `GoogleDriveProvider(client=...)` helper also accepts an already authorized Drive v3 client.

To export GGUF, use an `export` step with `model_path`, `format: "gguf"`, `output_path`, `outtype` (`f32`, `f16`, `bf16`, or `q8_0`), and `converter_path` pointing to an installed official llama.cpp `convert_hf_to_gguf.py` inside an unmodified Git checkout. Supported adapter architectures are GPT2 and Llama; the converter must support the model's tokenizer. The result records the converter revision and output SHA-256. No TFLite converter is provided.

Pipeline resume requires the unchanged `steps` definition, `resume: true`, and the selected published `.colab-bridge/checkpoints/pipeline-<run>/step-<N>/checkpoint.json` as `checkpoint_path`. Resume through a linked retry that restores parent artifacts. A standalone submission has no access to a previous job's files. Completed steps restore their selected inputs/outputs and are skipped. For arbitrary Python/shell/pip steps, list all files needed for later reproduction in `inputs` and `spec.artifacts`. Installed packages and other process/runtime side effects are not checkpoint artifacts: prepare the environment before resuming a pipeline.

LoRA resume uses `checkpoint_path: "<output_dir>/checkpoints/<run>-step-<N>"` (a directory). Its published selection marker is `<checkpoint_path>/checkpoint.json`. Checkpoints contain the adapter, optimizer, RNG state and references to immutable input model/JSONL snapshots. Restore all parent artifacts, not only the marker. Use the same model/data paths and LoRA settings; `max_steps` is the total desired step count. A retry can reuse `output_dir` when it contains only restored checkpoints; otherwise choose a new output directory. A checkpoint at the requested final step recreates final outputs without another optimizer step.

A new `resume: true` pipeline can begin without a checkpoint only when no previous attempt/source is claimed. A linked retry without a selected checkpoint fails. If the runtime disappeared before a checkpoint marker was published, there is no safe completed-step resume point: explicitly start a new run after deciding whether arbitrary-code effects can be repeated. The worker never silently replays those steps after a lost lease.

Checkpoint upload is independent of process supervision and lease renewal. Publication manifests contain only immutable workspace-relative files; the parent uploads and hashes them using its own fenced client, then acknowledges the manifest. Completion markers are registered after their referenced files. Failed, cancelled and timed-out jobs retain available checkpoints while their lease remains valid. A stalled publication drain is bounded and reported as incomplete. Local checkpoint existence alone does not prove cloud persistence.
